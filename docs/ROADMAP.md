# Whim Cart Dream — Product and engineering roadmap
Status: proposed baseline | 2026-11-27 | Repository: 11erorr583/whim-cart-dream

## 1. Mission and scope
Create a realistic, immersive virtual retail experience for people who want to experience shopping without real purchases or debt. It is a simulated shopping service, not a game, bank, marketplace or clinically validated addiction treatment. Every balance, receipt, order and delivery is clearly identified as simulated. No real payments, cash withdrawals, physical deliveries, card entry or real shipping addresses. Do not promise reduced compulsive shopping without evidence. Avoid scarcity, spend rewards, leaderboards, punitive streaks and engagement-maximizing mechanics.

Required: animated professional ecommerce, walkable 3D mall/mart, realistic products and sounds, persistent virtual vault, time and streak-based budget growth, order confirmation voice/phone calls, Python FastAPI. Standard accessible 2D shopping must remain available.

## 3. Architecture and stack
Retain React/TypeScript/TanStack Start and Tailwind initially; React Query for server data; React Three Fiber + Three.js + Drei for 3D, Rapier only if needed, Motion/GSAP selectively, Web Audio API for spatial sound. Python 3.12+ FastAPI modular monolith, Pydantic, SQLAlchemy 2, PostgreSQL, Alembic, pytest. Docker Compose local DB/API; use same-origin proxy and secure cookie sessions or short-lived tokens with rotating HttpOnly refresh cookies. Redis/Celery only when background workload warrants; begin with durable DB outbox and scheduled worker. OpenAPI-generated TS client. CI: lint, typecheck, tests, build, migrations and dependency/secret checks. CDN/object storage for licensed GLB/KTX2/audio. Twilio Voice or regional equivalent behind provider adapter and feature flag; no provider selected until pricing/availability/consent review.
Proposed layout:
- src/ existing frontend, features/{catalog,cart,checkout,vault,mall,audio,orders,account}
- backend/app/{api,core,models,schemas,services,repositories,workers}
- backend/alembic, backend/tests, docs/, tests/e2e, infra/
- public/assets/ for small licensed assets; external CDN for large assets.
Flow: browser -> HTTPS API -> auth/service -> PostgreSQL; transaction writes order + ledger + outbox atomically; worker processes delivery/call events; browser polls or subscribes to authorized events. 3D and 2D share product IDs/cart/API.

## 4. Domain and API contracts
Use UUIDs, UTC timestamps, foreign keys, integer minor units and ISO currency label with explicit virtual designation. Tables: users, sessions, user_preferences, vault_accounts, ledger_entries, budget_policies, accrual_periods, wellness_goals, wellness_days, products, variants, asset_manifest, carts, cart_items, wishlists, orders, order_items, order_events, call_consents, call_attempts, outbox_events. Index user/time and order/status; unique SKU, accrual(account,period,kind), checkout(user,idempotency_key), provider event ID. Ledger append-only; refunds are compensating entries. Account deletion/anonymization and retention policy must reconcile privacy and audit needs.
API v1:
- POST /auth/register, /auth/login, /auth/logout; GET /me; PATCH /me/preferences; DELETE /me
- GET /products?category=&q=&cursor=, /products/{id}, /mall/manifest
- GET /cart; PUT /cart/items/{variant_id}; DELETE /cart/items/{variant_id}; GET/PUT wishlist
- POST /checkout/quote; POST /orders (idempotency key, quote version); GET /orders, /orders/{id}; POST /orders/{id}/cancel
- GET /vault, /vault/transactions, /vault/budget; GET /wellness; PUT /wellness/goal
- POST /orders/{id}/calls (explicit consent); GET /orders/{id}/calls; POST /webhooks/voice (signature verification).
Use pagination, structured errors, validation and per-resource ownership. 409 insufficient balance/stale quote; no client-supplied totals trusted.

## 5. Virtual economy specification
Illustrative PKR pilot (currency and amounts not yet approved): opening 50,000; daily 500; seven eligible days 1,000; thirty eligible days additional 5,000. Base income accrues offline from server time; optional monthly income replaces rather than silently duplicates base allocation. Streak means elapsed days meeting a user-defined spending boundary or intentional pause, not time in app or number of purchases. No login requirement; missed days never erase funds, no urgency or shame. Allow pause and disable bonuses; cap bonus growth with transparent policy. Store timezone and policy version; server calculates elapsed eligible periods once, including missed worker runs; prevent duplicate accrual across timezone changes and concurrent requests. Use a neutral ledger showing opening funds, income, purchases and refunds; no withdrawability or real savings claims. Balance = sum posted credits minus debits. Lock account row, validate server quote and funds, insert order + debit + outbox in one transaction; idempotent retries return same order. Cancel eligible order once with compensating credit. Never allow negative balance or silently clamp.
Acceptance: two concurrent purchases cannot overspend; refresh/relogin/device switch preserves balance; offline accrual and DST boundaries correct; duplicate jobs and refunds do not duplicate funds; missed streak never confiscates money.

## 6. Retail experience and design
Architectural direction: warm stone, glass, brushed metal, neutral signage, natural lighting, restrained editorial typography and photography; no cartoon avatars, neon HUD, generic glowing gradients, confetti or game points. Homepage with real mall-style entrance, department directory, conventional search/catalog, account and vault. Mall route lazy-loads 3D after explicit entry. Start with one realistic supermarket aisle and checkout, then atrium, fashion, electronics and beauty departments. First-person or guided point-to-point navigation, keyboard/touch controls, collision boundaries, accessible exit, adjustable camera speed, no forced motion. Select product on shelf -> accessible detail overlay -> cart; 2D catalog shares state. Use actual-scale PBR assets, baked lighting, LOD, instancing, compressed textures, lazy loading and license manifest. No claim of photorealism until visual QA on target devices. Provide static/2D fallback for unsupported WebGL, low memory or reduced motion.
Audio: opt-in after user gesture; spatial footsteps, doors, trolley, ambient crowd, scanner, receipt printer, elevator chime, ringtone. Separate volume/mute controls, captions for voice, pause when tab hidden, no sudden loud sounds, no purchase celebration. Use licensed recordings and document attribution.

## 7. Orders and calls
Order state: placed -> confirmed -> processing -> simulated shipped -> simulated delivered; cancellation allowed by policy. Durable timestamps/events, no real courier dispatch, tracking IDs clearly virtual. In-app confirmation immediately available with audible speech, transcript, accept/decline and replay on request. Actual phone calls are opt-in, verified number only, clear automated simulated-order introduction, user-selected window, rate limit, quiet hours, opt-out, no recording by default, no unsolicited retries. Store minimum phone data encrypted and delete per policy; never ask for card or OTP during call. Provider credentials server-side; signed webhook, dedupe and failure fallback. Call statuses requested/ringing/answered/completed/declined/failed distinct from order state. Actual calls require provider account, regional availability, cost ceiling and legal/privacy review.

## 9. Security, quality and release gates
Threats: account takeover -> secure cookies, rate limits and password hashing/managed auth; IDOR -> ownership tests; wallet tampering/race -> transactional ledger; XSS/CSRF -> CSP, escaping and CSRF controls; webhook spoof/replay -> signature + event uniqueness; call abuse -> verified opt-in and caps; data exposure -> minimal PII, redacted logs, encrypted transport, secret manager; malicious assets -> trusted sources and validation. No secrets committed to public repo.
Tests: pytest unit + Postgres integration; Vitest component/domain; Playwright desktop/mobile flows, offline/error states, keyboard and accessibility; visual QA on actual 3D hardware. Test double submit, concurrent checkout, stale quote, refunds, accrual catch-up, timezone boundaries, cross-account access, failed call and fallback. CI required before merge. Provisional targets: 100 concurrent pilot users, API p95 <300ms for ordinary reads, LCP <=2.5s on representative 2D mobile, 30 FPS minimum on defined mid-tier 3D device, WCAG 2.2 AA for 2D and equivalent controls for 3D. Validate against measured baseline; no performance claim yet. Backups and restore drill, migration rollback plan, structured logs/metrics, alert on ledger mismatch/outbox failures. Stage deployment before production. Measure task completion, perceived realism, accessibility and voluntary wellbeing feedback rather than session length or spending volume.
